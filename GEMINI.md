# Grimborne Hunters («Охотники Мрака») — Главные правила и пульт AI-разработки

> **Обязательные правила для каждой сессии ИИ в этом репозитории.**

## 1. Обязательные правила общения и работы
1. **Язык:** всегда отвечать пользователю на **русском языке**, простыми и понятными словами (технические термины коротко пояснять).
2. **Ссылка на игру:** **после КАЖДОЙ правки или обновления** обязательно прикреплять кликабельную актуальную ссылку на GitHub Pages: `https://feesy1.github.io/grimborne-hunters/?v=<ТЕКУЩАЯ_ВЕРСИЯ>`.
3. **Причина, а не костыль:** при сообщении об ошибке сначала воспроизвести и установить корневую причину, проверить зависимые системы по `docs/SYSTEM_REGISTRY.md`, и только потом вносить минимальный чистый фикс.
4. **Не считать задачу готовой без проверки:** перед каждым пушем обязательно прогонять `tools/check_assets.py` и `tools/qa_smoke.py` (`console=0, page=0, http=0`, `FPS >= 60`), а визуальные изменения осматривать на живых скриншотах от уровня глаз.
5. **Остановка по приоритетам (без бесконечной доработки):** разделять задачи на **P0 (критическая)**, **P1 (важная)**, **P2 (желательная)**, **P3 (косметика)**. Не полировать P3, пока есть P0/P1.
6. **Не раздувать монолиты:** новые локации, механики и подсистемы выносить в отдельные чистые модули (`< 1500` строк) по образцу `js/souls/soulsSector01Slice.js` и `js/souls/soulsLocomotion.js`. В `combat.js`, `models.js`, `world.js` вносить только тонкие точки интеграции.

## 2. Паспорт проекта (актуально на `z106`)
- **Игра:** 3D Dark-Fantasy Souls-like Action RPG «Охотники Мрака» (*Grimborne Hunters*) — стиль *Dark Souls / Bloodborne / Elden Ring*.
- **Стек:** Vanilla ES Modules + Three.js `r160` (без сборщика) + Web Audio API + Blender 4.5.9 LTS (Draco GLB).
- **Репозиторий и деплой:** `D:\GrimborneHunters` → `https://github.com/Feesy1/grimborne-hunters.git` (ветка `main` → GitHub Pages).
- **Текущая фаза:** полировка и приёмка эталонного **Сектора 01 («01 • Выход из водоотвода»)** в `js/souls/soulsSector01Slice.js`. Сектора `02–08` сохранены в репозитории и временно отключены флагом `SECTOR01_VERTICAL_SLICE_MODE = true` в `js/souls/soulsExteriorShore.js` до утверждения стандарта Сектора 01.
- **Локальные инструменты на этой машине:**
  - Python: `D:\RGBMoCap\runtime\python.exe`
  - Blender 4.5.9 LTS: `D:\Blender\blender-4.5.9-windows-x64\blender.exe`
  - Локальный сервер: `server.ps1 -Port 8090`

## 3. Неприкосновенные инварианты (ЗАПРЕЩЕНО ломать)
- **Замок Пепла** (`js/soulsArena.js`, `soulsCastleLayout.js`, бой с боссом «Судья Руин», парирование, стойка, двери, костёр).
- **5-актовая кат-сцена побега** (`chasm_only`, `shaft_river`, `soulsEscapeCutscene.js`, `soulsBossLipSyncData.js`, точка пробуждения `wakePos = (0, 0.000, 2.5)`).
- **Метрика масштаба:** рост героя = **`1.60 м`**. Все 3D-ассеты строятся и проверяются в Blender рядом с манекеном `1.60 м`.
- **Матовый PBR и свет:** камень/земля `roughness 0.80–0.97`, `metalness: 0.0` (запрещены зеркальные лужи, пластиковый глянец, «нарисованные» оранжевые пятна и телепортирующиеся `PointLight`).
- **Единый источник истины (SSOT) для физики:** каждый твёрдый и разрушаемый объект в новой локации обязан регистрировать свой коллайдер в той же точке кода, где ставится меш.
- **Никаких рабочих скриптов, `.blend` и временных картинок внутри `D:\GrimborneHunters`** — все временные скрипты генерации хранятся вне репозитория (или в `scratch/` сессии).

## 4. Навигация по документации (`docs/`)
Перед началом задачи читай только нужные профильные документы:
- `docs/PROJECT_OVERVIEW.md` — цели, сюжетный маршрут, платформы, текущий этап.
- `docs/GAME_ARCHITECTURE.md` — карта модулей, схемы взаимодействия систем и пайплайны.
- `docs/SYSTEM_REGISTRY.md` — реестр всех 12 систем, их зависимости и зоны «не трогать без теста».
- `docs/VISUAL_STYLE_GUIDE.md` — канон визуала, света, материалов и таблицы реальных размеров (`1.60 м`).
- `docs/ASSET_PIPELINE.md` — стандарт создания Blender 4.5.9 Draco GLB + 4-панельное превью.
- `docs/LEVEL_DESIGN_GUIDE.md` — принципы Souls-like уровней Речного Предела и SSOT-коллизий.
- `docs/TECHNICAL_DECISIONS.md` — журнал принятых архитектурных решений (ADR), чтобы не откатывать решения назад.
- `docs/KNOWN_ISSUES.md` — актуальный список проблем по приоритетам P0–P3.
- `docs/CHANGELOG.md` — история ключевых сборок.
- `docs/TASK_BRIEF_TEMPLATE.md` — шаблон чёткого ТЗ для крупных задач.
